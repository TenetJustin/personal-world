# 07 · 路线决策、风险、替代方案与反方审查

技术证据见 [03](03_Open_Source_Research.md)，以下路线评分、切换门槛和优先级均为 [E] 工程判断，不是已经实现或跑分的结果。

## 1. 最终推荐

**首选 A：可编辑 PBR 网格作为可接近世界的主体，离线制作 / 光照预计算支撑画质；实时 Three.js WebGL2 负责相机、太阳直射、湖水、微动态与交互；React 负责真实 DOM 桌面与可访问内容。**

它最贴合本项目“有限观察 → 走近 → 穿门 → 屏幕 → 返回”的连续空间。保留真实几何和统一坐标，比把多个漂亮视图拼成场景更容易控制门窗、遮挡、相机和返回状态。摄影级表现仍依赖高水平资产制作、烘焙和美术验收，不是选对框架就自动得到。

**备用 B：以离线外观烘焙 / 重建表达静态部分，实时网格承担交互；有条件引入局部 Gaussian Splatting。** B 不是必须用 Splat 的路线，也不是更快更真实的普遍结论。没有合法多视角数据、可用离线设备或完整路径覆盖时，Splat 子路线不能启动。

## 2. 两条完整生产与运行路线

### A · 实时 PBR 为主

生产：自建参考 / CC0 → Blender 建筑与近景母版 → UV0 PBR / UV1 irradiance / 室内 probe → GLB + sidecar → Meshopt / KTX2 / LOD → 浏览器同镜头校准。地形生成与侵蚀离线处理；远峰可预渲染分层，但近林、岸石、建筑、电脑保留真实网格。

运行：单 Canvas / 单世界坐标，分块地形与实例化森林；实时直接太阳 + 已校准静态间接光；实时波场与 planar reflection；相机安全路径与资源 readiness；单一 DesktopRoot 投影接管到全屏 DOM；内容静态 HTML 可直达。

[A 的阶段验证] Phase 01 验 S01/S02 与水岸 / 光照机制；Phase 02 验完整室内；Phase 03 验连贯 / 中断 / 屏幕；后面才扩桌面、声音和发布。

### B · 离线外观与重建为重要主体

生产路线 B1（无需扫描训练）：Blender 高质量场景 → 同一批准光照下离线烘焙静态外观 / 分层背景 → 远景卡片、低模重投影或 baked mesh → 交互物体保留 PBR 网格 → 各层色彩、深度、反射代理统一。静态主体可以使用更接近 emissive / unlit 的完整外观，避免再被光照乘一次；玻璃、水、电脑等需要动态视角响应的部分单独保留实时材质。

生产路线 B2（局部 Splat）：有权使用的多视角静态拍摄 / 合法虚拟多视角数据 → 相机标定与覆盖检查 → 兼容离线设备上的 gsplat 类训练 → PLY 等输出 → SuperSplat 裁切 / 清理 / 格式转换 → Spark LoD / 预算 / 共同坐标 → 实时代理网格热点 / 碰撞 / 必要深度 → 同路径混合渲染测试。**SuperSplat 负责编辑，Spark 负责网页，训练另有工具与设备**；不把三者混为一项“一键生成”。

[F] [gsplat trainer](https://github.com/nerfstudio-project/gsplat/blob/512d366b67073d77ca099ede742683c165dfc23b/examples/simple_trainer.py) 默认 CUDA、支持 COLMAP 类数据与 PLY 导出，[源码许可](https://github.com/nerfstudio-project/gsplat/blob/512d366b67073d77ca099ede742683c165dfc23b/LICENSE) Apache-2.0；[setup](https://github.com/nerfstudio-project/gsplat/blob/512d366b67073d77ca099ede742683c165dfc23b/setup.py) / README 说明相关工具链。本轮未安装、训练或验证 Mac 原生生产；没有获准设备时，该环节为未就绪，不假定可以租云 / 上传数据。

运行仍保留一个 Three.js Canvas：静态背景 / Splat + 实时湖水 / 门 / 电脑 / 代理几何，共同 CameraDirector、RouteAdapter、DesktopRoot。DOM 交接方式与 A 相同，不能改用多个 iframe viewer 来掩盖空间割裂。

B 必须限制在采集 / 重建可信的视域和固定照明下。真实拍摄中的反光水、风动树叶、曝光不一致会挑战静态重建；把湖水与近树保留实时可以隔离部分风险，不能修复被拍摄进 splat 的旧反射或漂浮残影。人工清理、代理对齐和过渡通常比展示一个 splat 文件复杂得多。

## 3. 多指标比较

| 指标 | A · 实时 PBR + 预计算 | B · 离线外观 / 局部 Splat + 交互网格 | 项目取舍 |
| --- | --- | --- | --- |
| 静态摄影细节 | 依赖优质建模 / 扫描 / 材质与光照 | 数据好、视域内可很强；烘焙可接近离线效果 | B 可能更好，尚未用同镜头证实 |
| 走近、绕看与穿门 | 真实几何容易建立连续视差 / 门窗 | 缺失背面、投影拉伸、splat 边缘暴露风险更高 | A 占优 |
| 湖水 / 近岸反射 | 网格、深度与平面反射机制清楚 | 背景 / splat 需要反射代理，透明混合更复杂 | A 占优；B 不替代水体 |
| 动态太阳 / 灯光 | 直接光可变，但静态 GI 仍需固定 | 完整外观 / 普通 splat 更难重光照 | 两者首版都锁午后，A 可扩展性较强 |
| 微风 / 物体交互 | 叶片、门、电脑各有网格与材质 | Splat 变形不等于有物理材质 / 阴影 | 交互层仍以网格为主 |
| 浏览器性能风险 | 叶片 overdraw、draw calls、反射 / 阴影 | splat 排序、透明填充、带宽、数据解码；baked mesh 可便宜 | 没有统一胜者，必须同路径 / 同设备实测 |
| 内存 / 下载 | KTX2、实例共享、LOD 预算可控 | splat 高细节数据可能大；streaming / 格式压缩仍须视觉测试 | 不能把压缩下载大小当显存 |
| 资产生产 | 建模 / UV / 烘焙投入较高，编辑明确 | 捕获 / 训练 / 清理 / 代理对齐有隐藏成本；B1 更可控 | 小屋首选 Blender；B2 只在数据条件成立时选 |
| macOS 生产 | Blender 与网页链可作为候选，具体版本仍预检 | 浏览器播放与离线训练分离，CUDA 候选未在当前 Mac 验证 | 不要求本机跑不兼容离线链 |
| 页面内容 / 可访问性 | DOM 与静态内容层独立 | 同样可以独立 | 不由渲染路线决定，必须共用内容架构 |
| 更新与维护 | 改布局后重烘受影响部分，交互数据稳定 | 静态外观可能重烘 / 重建 / 重训，采集覆盖难增量 | A 更适合未来个人内容迭代 |
| 许可可控性 | 自制 + CC0 + MIT / Apache 代码可做清单 | 还要追踪照片 / 场地 / 扫描 / 训练实现 / 输出权利 | B 的授权链更长，不假定样例数据可用 |
| 过渡集成 | 真实门洞 / 屏幕空间明确 | 合成层、深度与 proxy 误差增加 | A 为首选，B 须通过完整路径 |

无数值“总分”：尚无相同资产、设备和镜头的基准，给一组精确分数会制造不真实的确定性。

## 4. 切换条件与止损次序

1. A 的 S01/S02 失败先定位原因。错误尺度、差树形、未校准光照并不证明实时渲染不行；先修因果，再复测。记录两轮修复各针对什么缺陷，不机械“试两次就换技术”。
2. 若主要瓶颈是**远景视觉 / 远林成本**，先用 B1 的离线远山 / 远林层；交互近景仍保持 A。批准的观察范围中不得出现滑动、错反射、无法走近的平面物体。
3. 若室内 PBR / GI 成本仍达不到目标且用户接受固定布局 / 太阳，可比较 B1 完整外观烘焙网格。必须保留可接近的电脑、视角反应必要的反射材质与窗口外共同世界。
4. 只有合法静态多视角数据、离线训练设备、可清理输出同时具备时，才比较 B2。没有数据就不把“未来也许扫一个房间”当备用落地保证。
5. B 对照必须使用同一 S01–S04、视角边界、进入 / 退出路径、1440×900 与相同设备 / 网络；视觉评分明显改善，且 p95、下载、内存与授权均达到同一预算，才提交路线切换决策。
6. 若 B 在门洞、反射、视差、透明排序任一处失败，返回 PBR / baked mesh 或收窄视域，经用户批准再调整；不默认删掉半自由探索，不能把整个网站替换成不可逆影片。

明确排除：把 OpenGL 离线 ray marcher 塞进 Three.js；把现代 WebGPU 当成 GLSL 430 的兼容层；把动态 GPU path tracing 的漂亮静止累计帧当持续运动画质；把全景图用于近距离绕看；把多个风格不同的 Demo 拼接当统一世界。

| 风险 | 触发信号 | 提前阻止 | 失败后的动作 |

## 7. 必须手工制作或人工审美验收

建筑母版与真实构造、门窗 / 屏幕 / 家具尺度、hero 针叶树和岸石轮廓、木纹方向 / 尺寸、湿度与苔藓分布、太阳与材质的共同校准、摄影机动机 / 速度 / 构图、自然声音剪辑都需要人的判断。程序 / agent 可以加速重复建模、导出、比较和记录，不承担最终审美签字。

尤其不能用相似度分数代替：原图以外的空间完整性、运动中摄影感、近岸光学、观看舒适度和桌面文字观感。所有标准镜头必须在浏览器原始输出中审查。

## 9. 反方审查：为什么 A 仍可能失败

**反驳一：A 需要的美术能力与工时可能超过“免费资产拼装”的现实投入。** 回应：成立。代码选型不能解决这一点。先用两镜头切片评估真实质量，未达标就投入手工修形 / 材质 / 灯光或缩小空间，不让大量桌面功能形成沉没成本。

**反驳二：固定太阳 + 烘焙仍可能像静态游戏场景。** 回应：成立。材质和光照能量、接触、植被轮廓、空气层次与镜头才是关键；不把“加 Bloom / DOF”当答案。太阳可以固定，但水、风和观看动作必须自然，动静之间没有矛盾。

**反驳三：直接用一组离线画面可能更快达到摄影感。** 回应：在固定视点成立，因此 B1 是有效备选。可是本任务要求接近、穿门、屏幕与返回；如果离线视图缺少连续视差，它不能满足原目标。B 的路线变更必须在原路径验证，不能通过删掉难点获得漂亮截图。

**反驳四：Splat 可以捕获更真实的房间，为什么不直接首选？** 回应：本项目尚无合法、完整、与虚构小屋匹配的数据集与采集条件；门窗 / 水 / 太阳 / 电脑都需要额外动态网格和混合处理。训练和清理不是免费得到，当前 Mac 也未验证 CUDA 生产链。具备条件后可在限定静态区域比较，但现在把它当主干会转移而非消除风险。

**反驳五：持久 Canvas + DOM + 路由增加复杂度。** 回应：成立。以唯一 CameraDirector、单一 DesktopRoot、独立 ContentRepository 和版本化 snapshot 减少互相写状态；仍需 Phase 03 的打断 / resize / 返回测试。若无缝接管失败，先用清楚的短过渡，保住内容、状态与空间方向。

首选 A 因为它对原要求的约束最可控，不是因为已证明它更快或一定照片级。

| 真实个人资料与发布环境 | 本轮只预留结构，后面单独讨论；不上传私人资料、不部署 | 内容填充 / 正式发布前 |

## 11. 审查者最终判断

**最可能导致视觉质量不达标的是资产、美术和摄影没有形成同一个世界，而不是 Three.js 缺少某个特效。** 相机一旦走近，重复纹理、粗糙树形、错误尺寸、缺乏接触和不一致光照会同时暴露；桌面做得再完整也无法补救。

提前阻止：只允许 Phase 01 先完成 S01/S02 的真实 browser 切片，使用接近最终品质资产，审查范围边界与运动而非单帧；保存原始性能与画面；由用户 / 美术负责人对单项评分和一票否决负责。任何核心项失败即返工 / 比较 B，直到视觉基础成立才扩展完整房间和应用。

本轮 Phase 00 在文档交付后停止。所有后续实验都是待批准的计划，不是已经进行的网站开发。
